# Project structure

- Place each application's entry code and dedicated platform code in its corresponding directory under `apps/`.
- Organize shared code as `packages/<domain>/<capability-package>/`; capability packages within a domain are independent packages named `@chorus/<domain>-<capability-package>` (such as `@chorus/agent-core` and `@chorus/sdk-client`), while `apps/desktop`, `apps/mobile`, and `apps/relay` have package names matching their directory names (`desktop`, `mobile`, and `relay`).
- Packages published to npm have fixed names: `packages/sdk/bundle` is `@chorus/sdk`, `apps/cli` is `@chorus/cli`, and subpackages for platform-specific CLI executables are `@chorus/cli-<os>-<architecture>` (such as `@chorus/cli-darwin-arm64`, with the `-musl` suffix for Linux musl builds); their manifests are generated by the workflow at release time.
- Set `"private": true` in manifests of unpublished packages.
- The directory tree below lists the main packages and their responsibilities; put new packages in the corresponding domain.
- Each application and capability package has a `README.md` at its root, with content requirements in [Documentation](../../chorus-documentation/SKILL.md#documentation).
- Applications compose features through shared packages rather than copying or reimplementing existing capabilities.

Organize source code within capability packages by feature:

```text
packages/<domain>/<capability-package>/
├── package.json           Package name, dependencies, and public exports
├── README.md              Package responsibilities, public entries, and usage
└── src/                   Source for this capability, further divided by feature
```

`apps/cli` is the unified terminal entry and starts `packages/ui/tui` through its public entry; command parsing and non-interactive commands do not initialize the terminal interface.

- Under Bun, the CLI and TUI load only `sdk/client`, `ui/tui`, and packages independent of host implementations; they do not load Node.js-side packages such as `services/agent-host`, `agent/*`, or `platform/*` in the Bun process (see runtime classifications below).
- The host manages the Agent execution loop.
- When used independently, the CLI starts a Node.js execution host as a subprocess and connects through `sdk/client`; it owns startup, readiness waiting, exit, and exceptional cleanup, and stops the host it started when exiting.

Validate the Agent core and Node.js-side packages only on Node.js (including the user's system Node.js and the Node.js embedded in Electron `utilityProcess`; main-process-only entries registered below are validated in the Electron main process). Native dependencies use Node-API, and CI covers the minimum version declared by `engines.node` and Electron's embedded Node.js; do not add Bun compatibility branches or Bun-specific APIs.

- Compile the CLI into platform-specific executables with `bun build --compile` and distribute them as platform-specific npm subpackages, with separate Linux glibc and musl packages.
- The execution host does not run inside the Bun-compiled executable; its JS artifacts reside in the main `@chorus/cli` package, and its Node-API native dependencies ship with the corresponding platform subpackage.
- The execution host runs on the user's system Node.js; the supported version range is declared by `engines.node` in the `@chorus/cli` manifest, and `devEngines` in the root [package.json](../../../../package.json) falls within that range.
- Before starting the host, the CLI checks the Node.js version against `engines.node` and reports an explicit error with the required version when unmet.
- Each CLI process connects only to the host it started; it does not discover, connect to, or stop hosts started by other processes (including the desktop application).

- The main entry of `@chorus/sdk` provides Agent embedding and capability composition; the `@chorus/sdk/client` subpath provides the host client.
- Source resides in `packages/sdk/agent/` and `packages/sdk/client/`; both are `private` internal workspace packages and are not published separately.
- The SDK's sole release package, `packages/sdk/bundle/`, builds them into the main entry and `./client` subpath and declares them in `exports`.
- The client subpath maintains an independent dependency boundary and does not load Agent execution-side implementations.
- After building, use `pnpm --filter @chorus/sdk check:package` to confirm valid manifests and type exports (publint and `@arethetypeswrong/cli`), and confirm the `./client` artifacts contain neither agent-side code nor Node-only modules.
- Determine release-package runtime dependencies from dependencies actually referenced by build output; do not declare internal packages.
- Applications and other internal packages depend directly on `sdk/agent` or `sdk/client`, not on the release package.
- Validate `sdk/client` in every runtime that actually uses it: Node.js (the minimum version declared by `@chorus/sdk`'s `engines.node` and the `devEngines` version; Electron's embedded Node.js is also within that range), Bun (the CLI's version), React Native (Hermes, mobile), and Electron renderer (transport provided through preload).
- Vitest and Jest run on Node.js, so their results do not establish behavior in Bun, Hermes, or Electron renderer: run the same `sdk/client` contract tests with `bun test` for Bun, and cover Electron renderer and Hermes with their respective end-to-end tests; mark them unverified when they cannot run.
- Declare the same Node.js range as `@chorus/cli` with `engines.node` in the `@chorus/sdk` manifest, state the supported TypeScript version range in its README, and have `check:package` perform a consumer type check with the minimum supported TypeScript version.

Mobile does not use `packages/ui/components` or `packages/ui/features`; these packages rely on DOM, Tailwind CSS, and shadcn and serve only the desktop renderer. Keep mobile interfaces in `apps/mobile/`, sharing only `contracts`, `sdk/client`, `ui/i18n`, and logic packages independent of DOM, React DOM, or Node with other clients. Mobile code does not import DOM-dependent packages, and shared logic packages do not import any interface implementations.

- Classify capability packages by where they run, and encode dependency rules accordingly in [.oxlintrc.json](../../../../.oxlintrc.json): Node.js-side packages (the execution host or a Node.js process embedding the SDK) are `services/*`, `agent/*`, `platform/*`, `adapters/*`, `extensions/*`, `identity/*`, `sdk/agent`, `remote/access`, `observability/telemetry`, and `observability/diagnostics`; packages also usable by clients are `contracts/*`, `sdk/client`, `ui/i18n`, `remote/device-identity`, `remote/transport`, and `observability/logging`, which depend on neither Node.js-specific modules nor DOM.
- Packages used only by particular interfaces are `ui/components`, `ui/features` (desktop renderer), and `ui/tui` (terminal); `remote/relay` runs on every relay deployment target, including Cloudflare Workers, so it imports only `contracts/*`, `observability/logging`, and `remote/device-identity` and no Node.js built-in module, and only its deployment entries in `apps/relay` import it (see [Remote connectivity](../../chorus-remote/SKILL.md#remote-connectivity)).

- The desktop main process uses only `contracts/*`, `observability/logging`, `sdk/client`, `ui/i18n`, and the following platform entries, without importing other Node.js-side packages or accessing databases: path, data-directory computation, and file read/write entries from `platform/filesystem`; the application-update entry from `platform/updates`; and the entry for creating `utilityProcess` from `platform/execution`.
- These two entries from `platform/updates` and `platform/execution` depend on Electron main-process APIs and are main-process-only: keep their source under `src/electron-main/` in each package, export them through a separate subpath, and allow imports only from the desktop main process (`no-restricted-imports` in [.oxlintrc.json](../../../../.oxlintrc.json) checks the import side).
- Split packages serving both sides (such as `voice/dictation`) by entry, with client entries containing only client-usable code.
- Register the classification of new capability packages or main-process-only entries in the two classification passages above (where packages run, and what the desktop main process may use).

- When the execution host needs main-process capabilities, it requests them through a dedicated channel provided by the main process, which validates the request's source and parameters.
- When the host launches Node scripts bundled with the application, use the unified entry in `platform/execution`: the desktop host requests through that channel, and the main process launches only by identifiers of fixed scripts inside the application bundle using `utilityProcess`, rejecting arbitrary paths or code; the CLI host launches them with the Node.js running it.
- Other host code does not directly call `child_process.fork` or set `ELECTRON_RUN_AS_NODE`; desktop release artifacts disable `RunAsNode` with Electron Fuses.
- Run third-party code such as plugins, MCP services, and external Runtimes in restricted processes under [Permissions and security](../../chorus-security-design/SKILL.md#permissions-and-security).

- Divide packages with similar responsibilities as follows, while continuing to register specific dependency directions in the dependency-direction rules: `services/scheduler` only triggers and delivers tasks by time or event; `services/jobs` handles background-job registration, output, waiting, cancellation, and completion notifications; `services/agent-host` composes capabilities and executes received tasks; `agent/workflow` defines task dependencies and orchestration steps, without managing processes or jobs itself.
- Execution traces in `services/session` are part of session records and support recovery and replay; traces in `observability/telemetry` serve export and diagnostics and are not a basis for recovery or replay.
- `services/retrieval` provides general content retrieval and indexing backends; `agent/memory` organizes and maintains long-term memory, using a retrieval interface defined in `contracts` and injected by the composition entry (implemented in `services/retrieval`), without building another retrieval backend.

The remote domain (`contracts/remote`, `remote/*`, and `apps/relay`) follows [Remote connectivity](../../chorus-remote/SKILL.md#remote-connectivity), which defines package roles, connection paths, encryption and pairing, relay nodes, and deployment targets.
